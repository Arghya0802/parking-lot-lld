01 · Design mindset

Learn the reasoning, not a diagram

Follow a repeatable sequence: clarify scope, state invariants, separate responsibilities, expose atomic boundaries, choose a concurrency strategy, test failure paths, then optimize from measurements.

ClarifyScope, scale, storage
ProtectInvariants and transactions
SeparateDomain, policy, storage
EvolveMeasure before optimizing
Senior ruleCorrectness is defined by business invariants—not by the presence of a lock or the number of patterns.
02 · Requirements

Define the boundary before classes

First-version scope

Multiple floors and gates; typed spots and vehicles; allocation; ticketing; pricing; payment; release; availability display; out-of-service spots.

Defer deliberately

Reservations, valet, license-plate recognition, subscriptions, dynamic pricing, charging billing, and multi-region operation.

Questions a senior engineer asks

Single process or multiple service instances?

A JVM lock protects only one process. Multi-instance correctness belongs in authoritative shared storage.

What does “best spot” mean?

Nearest, lowest floor, any compatible spot, accessible eligibility, and reservations require different policies and indexes.

What failures must recover?

Duplicate gate events, timeout after allocation, payment success followed by local failure, crashes, and stale display projections all need explicit behavior.

03 · Invariants

State what must never break

Spot ownership

One spot has at most one active ticket; only its owning ticket releases it.

Ticket consistency

Every active ticket points to exactly one occupied spot.

Payment safety

One idempotency key produces at most one charge.

Availability truth

Out-of-service or occupied spots are never allocatable.

Atomic boundaryOccupying a spot and creating its ticket form one business transaction. Two thread-safe maps do not make two updates atomic together.

05 · SOLID

Control change and dependency direction

S — Single responsibility

Allocation, pricing, storage, payment, and orchestration change independently.

O — Open/closed

Add a policy implementation without rewriting the workflow.

L — Liskov substitution

Every adapter preserves the contract, including idempotency.

I — Interface segregation

Displays read availability without receiving mutation methods.

D — Dependency inversion

Workflow code depends on ports, not SQL or SDK classes.

Do not over-abstractSOLID does not mean maximizing interfaces. Add an abstraction at a real change, ownership, test, or technology boundary.

07 · Concurrency foundations

The double-booking race

Gate A
read A-17 → AVAILABLE
create T-101
write A-17 → T-101
⚡
Gate B
read A-17 → AVAILABLE
create T-102
write A-17 → T-102
Broken invariantBoth requests can report success, while one write overwrites the other. This is a compound check-then-act race.
Atomicity

Observers see all of an operation or none.

Visibility

One thread sees another thread’s writes.

Ordering

Operations are observed in a valid order.

volatile helps visibility and ordering, but it does not make count++ or “if available, occupy” atomic.

08 · Concurrency tools

Choose by scope and contention

Mutex / ReentrantLock

Exactly one owner protects a critical section. Best first choice for one in-memory aggregate.

Semaphore

Bounds concurrent permit holders. Good admission control; not authoritative inventory.

Atomic variable / CAS

Conditionally changes one memory location. Good for counters and compact immutable states.

Database transaction

Protects multi-record invariants across service instances.

Mutex

private final Lock stateLock = new ReentrantLock();

public ParkingTicket park(Vehicle vehicle) {
    stateLock.lock();
    try {
        return allocateUnderLock(vehicle);
    } finally {
        stateLock.unlock();
    }
}

Semaphore

private final Semaphore entryCapacity = new Semaphore(20, true);

public ParkingTicket handleEntry(ParkVehicleCommand command) {
    if (!entryCapacity.tryAcquire()) {
        throw new EntryBusyException("All entry permits are in use; retry shortly");
    }
    try {
        return parkingUseCases.park(command);
    } finally {
        entryCapacity.release();
    }
}

Atomic compare-and-set

private final AtomicReference<SpotOccupancy> occupancy =
        new AtomicReference<>(SpotOccupancy.available());

public boolean tryOccupy(TicketId ticketId) {
    return occupancy.compareAndSet(
            SpotOccupancy.available(),
            SpotOccupancy.occupiedBy(ticketId));
}
Scope warningJVM locks and atomics do not coordinate other service instances. Multiple atomics also do not automatically form one transaction.
09 · Database locking

Optimistic vs pessimistic locking

Optimistic

Read without locking, then write only if status and version are unchanged. Best when conflicts are uncommon.

Pessimistic

Lock a candidate before mutation. Useful for hot rows and short transactions; introduces waits and deadlock risk.

Optimistic conditional write

UPDATE parking_spot
SET status = 'OCCUPIED',
    current_ticket_id = :ticket_id,
    version = version + 1
WHERE spot_id = :spot_id
  AND status = 'AVAILABLE'
  AND version = :expected_version;

One affected row means this request won. Zero means a conflict: try another bounded candidate or return a controlled outcome.

Pessimistic candidate claim

BEGIN;
SELECT spot_id, version
FROM parking_spot
WHERE floor_id = :floor_id
  AND spot_type IN (:compatible_types)
  AND status = 'AVAILABLE'
ORDER BY distance_from_entry, spot_id
FOR UPDATE SKIP LOCKED
LIMIT 1;

UPDATE parking_spot
SET status = 'OCCUPIED', current_ticket_id = :ticket_id,
    version = version + 1
WHERE spot_id = :spot_id;
INSERT INTO parking_ticket (...) VALUES (...);
COMMIT;
FactorOptimisticPessimistic
Conflict rateLow/moderateHigh/hot rows
LoserDetects and retriesWaits or skips
Main riskRetry storm/starvationWaits/deadlocks
PracticeBound retries and side effectsShort transaction, fixed lock order
10 · Reference design

Start coarse-grained and correct

A first in-memory implementation can protect spot selection, occupancy, and active-ticket creation with one lock. It limits throughput but makes the atomic boundary obvious.

public final class ThreadSafeParkingLot {
    private final Map<SpotId, MutableSpot> spotsById;
    private final Map<TicketId, ParkingTicket> activeTickets = new HashMap<>();
    private final SpotAllocationPolicy allocationPolicy;
    private final Lock stateLock = new ReentrantLock();
    private final AtomicLong ticketSequence = new AtomicLong();
    private final Clock clock;

    public ParkingTicket park(Vehicle vehicle) {
        Objects.requireNonNull(vehicle, "vehicle is required");
        stateLock.lock();
        try {
            ParkingSpotSnapshot selected = allocationPolicy
                    .rankCandidates(vehicle, availableSnapshots())
                    .stream().findFirst()
                    .orElseThrow(() -> new ParkingFullException(
                            "No compatible spot is available for " + vehicle.type()));
            TicketId ticketId = new TicketId(
                    "T-" + ticketSequence.incrementAndGet());
            MutableSpot spot = spotsById.get(selected.id());
            spot.occupy(ticketId);
            ParkingTicket ticket = ParkingTicket.open(
                    ticketId, vehicle, spot.id(), clock.instant());
            activeTickets.put(ticketId, ticket);
            return ticket;
        } finally {
            stateLock.unlock();
        }
    }
}

11 · Reliability

Correct retries belong in the LLD

Idempotency

Persist unique operation/request IDs and results so retries converge.

Constraints

Reinforce ownership, valid states, and active-ticket uniqueness in the database.

Transactional outbox

Commit business state and event together; publish afterward to idempotent consumers.

Payment reconciliation

Use pending state and provider idempotency. Never hold a lock over a network call.

Cache ruleA cache may find candidates, but an authoritative conditional write or transaction decides the winner.
12 · Testing

Assert invariants under collision

Unit

Compatibility, ranking, pricing boundaries, legal state transitions, wrong-owner release, idempotency.

Concurrent

One spot and 100 synchronized callers must produce exactly one success.

Integration

Conflict, rollback, duplicate request, deadlock retry, outbox, and payment recovery.

Metrics

p99 latency, conflict rate, retries, lock waits, deadlocks, and reconciliation lag.

Testing limitA latch increases collision probability but does not prove every interleaving. Repeat stress tests and assert system-wide invariants.
13 · Common mistakes

Attractive but incomplete solutions

“Use ConcurrentHashMap”

It does not make a cross-map workflow atomic.

“Make status volatile”

Visibility is not compound atomicity.

“Semaphore equals free spots”

Permits drift and do not identify a spot.

“Use a Singleton”

It hides dependencies and stops at one process.

“Lock through payment”

Network calls amplify latency and failures.

“Retry forever”

Unbounded retry causes overload and duplicates.

15 · Senior takeaways

Carry these into every LLD

  • Invariants define correctness; a lock is an implementation mechanism.
  • The atomic boundary matters more than the class count.
  • Thread safety in one process and consistency across instances are different problems.
  • Mutex means exclusion, semaphore means permits, and atomic CAS means one-value transition.
  • Optimistic locking detects conflicts; pessimistic locking reserves before mutation.
  • SOLID controls reasons for change and dependency direction.
  • Idempotency, constraints, recovery, and observability are design concerns.
  • Start with the simplest correct approach, measure, and evolve deliberately.
