01 · Mental model

Reason in this order

Do not begin by listing classes. First define the promise your system must keep when many requests arrive together.

1 · ClarifyRequirements, scale, storage, failure model
2 · ProtectInvariants and atomic boundaries
3 · SeparateDomain, policy, orchestration, infrastructure
4 · EvolveMeasure contention before optimizing
The central design choiceBoth the occupied spot and active ticket live in one immutable LotState. Replacing that state is the transaction, so observers never see half of an allocation.
02 · Invariants

What must always remain true?

One owner

A spot has at most one active ticket.

Two-way consistency

An active ticket points to one occupied spot carrying that ticket ID.

Exact release

Only the ticket that owns a spot can release it.

Atomic transition

Spot and ticket changes become visible together.

Bounded work

Optimistic conflicts have a retry limit.

Admission control

A semaphore limits work but never owns inventory.

RememberA thread-safe collection protects its own methods. It does not make updates across multiple collections one business transaction.

06 · Concurrency cheatsheet

Each mechanism solves a different problem

Mutex

One owner enters a critical section. Used by pessimistic mode for the complete transition.

Semaphore

N permits bound concurrent work. It does not identify or own a parking spot.

Atomic variable

Ticket counters increment safely. Java/C++ atomically swap state pointers/references.

Immutable state

Readers can share snapshots without seeing objects mutate underneath them.

Thread safety

The class preserves its contract under supported concurrent calls without caller locks.

Version

Every committed transition increments state version, making conflicts observable.

Python nuanceThe Python standard library has no portable lock-free AtomicLong or object CAS. The implementation provides the same semantics with a short internal lock; do not rely on the GIL as your design contract.
07 · Locking modes

Optimistic detects conflicts; pessimistic prevents overlap

Optimistic flow

Read snapshot → compute candidate transition without a long lock → swap only if snapshot is still current → retry a bounded number of times.

Pessimistic flow

Acquire mutex → read, select, and build while holding it → replace state → release in finally/RAII/context manager.

QuestionOptimisticPessimistic
Best whenConflicts are uncommonState is consistently hot
Losing callerRetries from a fresh snapshotWaits for the lock
Main riskRetry storm or starvationLock wait or deadlock
Safety practiceBound retries; side effects after commitShort scope; fixed lock ordering
Multi-instance production analogueVersioned conditional DB updateSELECT ... FOR UPDATE
Why whole-state CAS?The example copies maps/tuples intentionally. It trades memory and write cost for an obvious atomic invariant. Production persistence would use one short database transaction, constraints, and bounded candidate queries.

Why IDs may have gaps

An optimistic attempt can allocate a ticket ID and then lose the state race. Unique, monotonic IDs do not need to be gapless. Requiring gapless IDs creates unnecessary serialization.

10 · Interview prompts

Test whether you can explain the design

Why not just use ConcurrentHashMap / a concurrent dictionary?
It protects individual map operations. The invariant spans a spot update and ticket insertion, so the complete transition needs one atomic boundary.
Why is volatile insufficient?
It provides visibility and ordering but does not make a compound check-then-act sequence atomic.
Why is the semaphore not initialized from free spots?
Permits can drift after crashes or maintenance and do not identify which spot belongs to a ticket. It is admission control, not inventory truth.
When would you choose pessimistic locking?
When contention is predictably high, conflicts are costly, and the protected transaction can remain short with deterministic lock ordering.
How does this evolve to multiple service instances?
Move the transaction into shared storage: versioned conditional updates or row locks, database constraints, idempotency keys, and a transactional outbox.
Why inject Clock and strategies in production code?
Clock makes time deterministic in tests. Strategy interfaces isolate policy changes from use-case orchestration and support focused substitutes.
